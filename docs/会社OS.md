# 📐 会社OS 仕様書
## AIマネージャー主導・1人アプリ開発会社（最終確定版）

本仕様書は、  
**社長1人＋AI（GitHub Copilot / マネージャーAI）によって  
アプリ開発事業を安全・継続的に運営するための最上位ルール**を定義する。

本書に反する提案・実装・判断はすべて無効とする。

---

## 1. 基本思想

- 人間（社長）は「意思決定」のみを行う
- AIは「実行・整理・記録」を担当する
- AIは賢くなくてもよい  
  **仕組みによって暴走しないことを最優先する**

---

## 2. 役割定義

### 2.1 社長（CEO）

#### 責務
- 事業方針の決定
- 仕様確定・変更の最終承認
- 実装フェーズへの移行判断
- リリース判断

#### 禁止事項
- 実装方法への過度な介入
- 文書を介さない口頭・一時的判断

---

### 2.2 マネージャーAI（Copilot / オーケストレータ）

#### 責務
- 企画 → 仕様 → 実装 の工程管理
- Gate（品質ゲート）判定
- 手戻り原因の分類
- Git運用の実行
- CEO_DASHBOARD の更新
- docs 配下の整合性維持

---

## 3. Single Source of Truth（正の定義）

以下のファイルのみを **正式な真実** とする。

```
docs/
├─ CEO_DASHBOARD.md   （社長の判断UI）
├─ PRD.md             （企画）
├─ SRS.md             （仕様）
├─ TASKS.yaml         （WBS）
├─ DECISIONS.md       （最終判断ログ）
└─ CHANGELOG.md       （変更履歴）
```

会話・一時的出力・メモは正としない。

---

## 4. 文書言語ルール（必須）

- **すべての公式文書は日本語で記述する**
- 英語のみの仕様書・判断文書は禁止
- 例外：
  - プログラミング言語構文
  - API固有名詞
  - エラーメッセージ原文  
  ※必要に応じ日本語で補足説明を付ける

## 5. 工程管理（ライフサイクル）

```
IDEA
→ PRD_DONE
→ SRS_DONE
→ IMPLEMENTING
→ TESTING
→ RELEASE
```

Gate 未達の状態で次工程へ進むことは禁止する。

## 6. 品質ゲート（Gate）

### Gate A：PRD
PRD.md には以下が必須。
- 背景・課題
- ターゲットユーザー
- やらないこと（スコープ制御）
- 成功の定義（KPI）

---

### Gate B：SRS
SRS.md には以下が必須。
- 画面一覧
- 画面遷移
- データ定義
- 集計ロジック（境界条件含む）
- エッジケース
- 非機能要件

---

### Gate C：実装
- SRS.md に準拠していること
- 想定エッジケースが破綻していないこと
- 重大バグが残っていないこと

---

## 7. 手戻り管理（必須）

修正時は必ず原因を分類し、戻す先を明示する。

| 原因 | 戻す先 |
|---|---|
| 仕様欠落 | SRS.md |
| 実装バグ | コード |
| 要件変更 | PRD.md |
| UI/UX不満 | SRS.md |

変更は CHANGELOG.md に記録する。

## 8. CEO_DASHBOARD 仕様

### 8.1 目的
社長が **「今、判断すべきこと」だけに集中するためのUI**。

### 8.2 編集権限
- AIが編集してよい：
  - 工程ステータス
  - 判断候補の列挙
  - 進捗・手戻り要約
- CEOのみが編集：
  - 事業コンパス
  - 最終判断ログ

## 9. Git運用方針（AI委任）

### 9.1 基本方針
- Git管理は必須
- Git操作の大部分は **AIに委任**
- Gitは「コード管理」ではなく  
  **意思決定・仕様変更の履歴装置**

---

### 9.2 役割分担

#### AIが行ってよいこと
- 変更ファイル確認・分類
- commit単位の整理
- 日本語commitメッセージ生成
- git add / commit
- 差分要約
- rollback提案

#### CEOが行うこと
- 判断を正式記録に残すかの決定
- PRD / SRS / 本仕様の変更承認
- push 承認
- リリース判断

---

### 9.3 Git運用ルール
- ブランチは main のみ
- 1 commit = 1 意味
- commitメッセージは日本語
- DECISIONS.md は必ず独立 commit
- AIは勝手に push してはならない

---

## 10. commit → CEO_DASHBOARD 連動ルール

### 10.1 基本原則
- commit = 事実
- CEO_DASHBOARD = 判断UI
- DECISIONS = 最終決定ログ

---

### 10.2 commit種別別ルール

#### 仕様変更（PRD / SRS / 会社OS）
- CEO_DASHBOARD に
  「要確認：仕様が変更されました」
  を必ず表示
- CEO承認前に次工程へ進まない

---

#### 判断ログ（DECISIONS.md）
- CEO_DASHBOARD の判断項目を整理
- 工程ステータス更新が必要なら反映

---

#### 実装commit
- 原則 CEO通知不要
- 判断が不要な旨を記載してよい

---

#### 手戻り・rollback
- CEO_DASHBOARD に
  「要判断：手戻りが発生」
  を必ず表示

## 13. FCF (フリーキャッシュフロー) 最重要方針

本事業における最上位KPIは **フリーキャッシュフロー（FCF）** である。

### 13.1 基本定義（本事業専用）
FCF ＝ 売上 −（Apple手数料＋外注費＋ツール費＋税金）

※ オーナー人件費・減価償却・設備投資は原則考慮しない。

---

### 13.2 位置づけ
- FCF は本事業における **最重要KPI** とする
- 利益・DL数・ユーザー数より優先される
- 経営判断は「FCFが増えるか？」を基準に行う

---

### 13.3 判断原則（必須）
以下に該当する施策は原則実行しない。
- FCFを減少させる可能性が高い
- FCFへの影響が説明できない
- FCF改善の仮説を持たない機能追加

---

### 13.4 停止ルール（明文化）
以下の条件を満たした場合、新規開発を停止する。
- 3ヶ月連続でFCFが横ばいまたはマイナス
- 改善施策を実施してもFCFが回復しない

その場合は「保守のみ」フェーズへ移行する。

---

### 13.5 FCF入力・集計の自動化

#### 入力方式（半自動化）
- **原本**: `data/fcf_input.csv`
- **入力者**: CEO（月1回、売上確定後に1行追記）
- **形式**: CSV（month, app_name, sales, apple_fee, external_cost, tool_cost, tax）
- **管理**: Git必須（履歴を残す）

#### FCF計算式（自動）
```
FCF = sales - (apple_fee + external_cost + tool_cost + tax)
```

※ 人件費は含めない（会社OS基本定義による）  
※ 空欄は 0 として扱う

#### AI処理フロー（自動実行）
CEOが「今月のFCFレビューを実行してください」と指示した際、AIは以下を実行する。

1. **data/fcf_input.csv を読み込み**
2. **各行のFCFを計算**
3. **月別・アプリ別に集計**
4. **前月比・3ヶ月平均を算出**
5. **docs/FCF_REPORT.md を生成・更新**
6. **docs/CEO_DASHBOARD.md のFCF欄を更新**
7. **判断が必要な事項のみCEOに提示**

※ AIは数字の解釈や評価を行わない。判断はCEOが行う。

---

### 13.6 アプリ別FCF判断ルール

複数アプリを運営する場合、以下の原則に従う。

| FCF状態 | 対応方針 |
|---|---|
| 🟢 増加している | 機能改善・投資を検討してよい |
| 🟡 横ばい | 改善施策は最小限。新規開発は慎重に |
| 🔴 減少・マイナス | 原則、新規開発停止。保守のみ |

**停止の最終判断はCEOが行う。AIは提案のみ。**

### 13.8 機能別FCF分析

#### 目的
「どの機能が金を生み、どの機能がコストだけ食っているか」を感覚ではなく数字で判断する。

#### 機能FCFの定義
```
機能FCF ＝ 機能由来売上 − 機能維持コスト
```

#### 売上配賦ルール
- 売上が直接紐づかない場合は **仮配賦** を使う
- 仮配賦基準：「課金動機への貢献度」または「Premium機能の利用率」
- 完璧な精度は求めない（意思決定できればOK）

#### 機能定義
- **原本**: `docs/FEATURES.md`
- **レポート**: `docs/FEATURE_FCF_REPORT.md`（AI自動生成）
- **管理**: Git必須（機能の追加・削除は重要な経営判断）

#### 機能別判断ルール

| 機能FCF状態 | 対応方針 |
|---|---|
| 🟢 プラス | 改善・強化を検討してよい |
| 🟡 ゼロ | 最小メンテナンスのみ。新規投資は慎重に |
| 🔴 マイナス | 原則、削除または他機能への統合を検討 |

**最終判断はCEOが行う。AIは提案のみ。**

### 13.9 FCF再投資ルール

#### 基本思想（最重要）
**「儲かってから攻める」**  
**「攻めてから儲ける」はやらない**

#### 投資原資ルール
- 再投資の原資は **FCFのみ** とする
- 借入・持ち出しは禁止
- 生活費とは完全分離

#### 投資トリガー（数値ルール）
以下の条件を **すべて満たした場合のみ** 投資を検討してよい。

1. **月次FCFが3ヶ月連続プラス**
2. **かつ、3ヶ月平均FCF ≥ 10,000円**

※ この条件を満たすまで投資は原則禁止

#### 投資配分ルール（目安）
FCFの使い道：

- **50%**: 内部留保（安全資金）
- **30%**: 外注（開発・デザイン）
- **20%**: 広告・ASO

※ この比率は固定ではなく、状況に応じてCEOが調整する。

---

### 13.10 外注判断ルール

#### 外注OK条件（すべて満たす必要あり）
1. **投資トリガー条件を満たしている**（13.9参照）
2. **外注対象機能が「機能FCFプラス」である**
3. **外注後、FCFが増える仮説が説明できる**
4. **失敗しても撤退できる金額である**（留保金の範囲内）

#### 外注NG条件（いずれか該当で禁止）
- FCFがマイナス・横ばいの状態での外注
- 仮説が不明確な「とりあえず外注」
- 留保金を超える外注費

#### 外注判断の記録
すべての外注判断は `DECISIONS.md` に記録し、実行結果を追記する。

---

### 13.11 広告判断ルール

#### 広告OK条件（すべて満たす必要あり）
1. **投資トリガー条件を満たしている**（13.9参照）
2. **広告対象アプリがFCFプラスである**
3. **CAC（獲得単価）＜ 月次LTV の仮説がある**
4. **1ヶ月で効果測定できる金額・期間である**

#### 広告NG条件（いずれか該当で禁止）
- FCFがマイナス・横ばいの状態での広告
- LTV試算ができていない
- 長期契約・大型予算の広告

#### 広告判断の記録
すべての広告判断は `DECISIONS.md` に記録し、実行結果を追記する。

---

### 13.12 投資判断の経営ループ

```
FCFが溜まる
 ↓
投資トリガー判定（AI）
 ↓
投資候補の提案（AI）
 ↓
```

### 13.13 アプリ売却（Exit）判断ルール

#### 基本思想（重要）
アプリは「作るもの」ではなく **「育てて、条件が揃ったら売る資産」** である。  
感情・思い入れは禁止。数字だけで判断する。

#### 売却判断に使うKPI
以下の3つのみを使用。DL数・レビュー数・SNS話題性は一切使わない。

1. **月次FCF**
2. **FCFの安定性**（変動幅）
3. **運用負荷**（社長の時間）

#### 売却トリガー（明文化）
以下を **すべて満たした場合** 、売却検討フェーズへ入る。

1. **月次FCFが6ヶ月以上連続プラス**
2. **直近3ヶ月のFCF変動が ±20%以内**（安定している）
3. **機能追加なしでもFCFが維持されている**
4. **社長の運用関与が「月5時間以下」**

**→ 「安定して儲かるが、伸び代が小さい」= 売却に最適**

#### 想定売却価格の算定ルール
```
想定売却価格 ＝ 月次FCF × 倍率
```

| 状態 | 倍率 |
|---|---|
| 個人運営・属人的 | 12〜18倍 |
| 自動化済み | 18〜30倍 |
| 複数アプリ横展開可能 | 30倍以上 |

**重要**: 倍率は「コード品質」より「運用の自動化度」で決まる。

#### 売却準備（デューデリジェンス・パッケージ作成）
売却判断を行った場合、直ちに以下を実行する。

1. **デューデリジェンスチェック**: `docs/EXIT_DUE_DILIGENCE.md` を埋める
2. **パッケージ生成**: `docs/EXIT_PACKAGE_SPEC.md` のプロンプトを実行し、資料一式を揃える

#### 売却判断の記録
すべての売却判断は `DECISIONS.md` に「売却判断用テンプレート」で記録する。

### 13.14 アプリ停止（Kill）と資産化ルール

#### 基本思想（超重要）
**アプリは失敗しても失敗させない。**  
「止めた＝損」ではない。再利用できた時点で勝ち。

#### アプリ停止トリガー（FCF基準）
以下の **いずれかを満たした場合**、停止検討フェーズへ入る。

1. **3ヶ月連続でFCFがマイナス**
2. **改善施策を2回実施してもFCFが回復しない**
3. **機能FCFが全体的にマイナス**

#### 停止後の資産化フロー（必須）
```
停止判断
 ↓
資産棚卸し（ASSETS.md更新）
 ↓
再利用タグ付け
 ↓
アーカイブ（archive/アプリ名/）
```

**絶対にやること**: 
- コード・仕様・ノウハウを `docs/ASSETS.md` に記録
- 再利用タグ（`#billing`, `#calendar_ui` など）を付与
- アーカイブに保管（消さない・凍結する）

#### アーカイブ構造
```
archive/
 └─ アプリ名/
     ├─ code/（ソースコード一式）
     ├─ specs/（PRD/SRS/DECISIONS）
     ├─ data/（実績データ）
     └─ ASSETS.md（抽出した資産のまとめ）
```

#### 再利用タグの重要性
次のアプリで「#billing」って言えば課金処理が再利用できる状態にする。  
開発時間を1/3に短縮できる。

#### 停止判断の記録
すべての停止判断は `DECISIONS.md` に記録し、資産化完了も追記する。
